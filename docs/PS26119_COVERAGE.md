## Engineering-track issue, not a PS requirement: #297

#297 asks for a sweeping refactor of the solver dispatch layer into a pluggable
`SolverEngine` interface, with a 45-item Definition of Done spanning a capability model, a
solver registry, checkpoint/warm-start/interrupt abstractions, thread-safety and memory-
ownership documentation, and eight separate new test categories - explicitly across the
whole of `src/core`, `src/simplex`, `src/pdhg`, `src/ipm`, `src/qp`, `src/mip` and the CLI/
Python surfaces, while everything currently on `main` keeps working and every existing
benchmark CSV stays comparable.

That is real, valuable, multi-week architectural work, and several of the properties it
asks for already exist piecemeal - `solve()` in `src/core/solve.cpp` is already a single
dispatch point classifying LP/MILP/QP/MIQP and routing to one engine each; `SolveControl`
(#223) is already a shared interrupt/progress abstraction every engine takes; `ResourceLimits`
/ `StopController` (#289) already unify resource-limit handling; `checkpoint.{hpp,cpp}` (#287)
and `solution_pool.{hpp,cpp}` (#225) already exist as their own modules. What #297 asks for on
top of that - a formal `SolverEngine` interface and registry, a capability model, and the
remaining ~40 items - has not been attempted here: doing it correctly means touching every
engine at once, and doing it under deadline pressure, in one session, without first breaking
the whole thing into independently reviewable pieces, is exactly the trade `ENGINEERING_RULES.md`
warns against (a wrong answer scores zero; a missing feature scores partial).
Recommended next step, if this is picked back up: split the 45-item Definition of Done into a
handful of independently landable PRs (interface + registry first, migrating one engine at a
time behind it, with the existing dispatcher as the fallback until every engine has moved),
each gated the normal way - build clean, full suite green, no benchmark CSV regression -
rather than one PR that has to get all 45 right at once.

Status after #402 (2026-09-22): the interface, the capability model, the registry and the selector exist in `src/solver_engine/`, with every built-in engine wrapped over its existing `solve_*()` function, and `solve()` reads two things from them, the LP engine's name and its warm-start capability, through the same `select_engine()` rule table as before, so no numerical path changed and the demo and the Netlib small tier re-run identically. What it is not yet: a single place that decides, since the CLI's accepted-name list in `src/util/options.cpp`, the name-to-function branches in `solve.cpp` and the registry are three copies, the classifier exists twice, and `engine::solve()` in `src/solver_engine/solver_engine_dispatch.cpp` is a narrower entry point than `solve()` (no presolve, limits or polish; it does run the status guard). The remaining items of the Definition of Done stay open on #297. The follow-up that closed three of the gaps named above (one classifier, `engine::classify`, for the dispatcher and the registry; the option table's `algorithm` choices held to `SolverRegistry::algorithm_names()` by a test; `sankhya engines` with `--format json`, every flag read from the engine) also made an LP engine named for a MILP, QP or MIQP a warning and a note on the answer rather than a silent no-op. What stays open is `engine::solve()` being narrower than `solve()` (no presolve, limits or polish, by its header's own account) and the dispatch branches in `solve.cpp` being by engine name, which is the design: an engine registered without a branch is refused, not run as another.
