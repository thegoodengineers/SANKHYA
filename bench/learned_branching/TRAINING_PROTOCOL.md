# Learned Branching Training Protocol (Issue #801)

This document specifies the exact protocol for collecting offline training data and generating the learned branching rule, ensuring strict compliance with Issue #801 requirements.

## 1. Disjoint Training Instances
To rigorously validate offline learning, the training dataset MUST be completely disjoint from all reported instances. 
The repository currently reports performance on the following sets:
- **MIPLIB 2017 (Tier 1)**: 30 instances (tracked in `data/miplib/manifest.json`).
- **MIPLIB 2017 (Tier 2)**: 60 instances (tracked in `bench/runners/miplib_tier2.json`).
- **MIPLIB 3**: ~60 classic instances (tracked in `data/miplib3/manifest.json`).
- **Netlib / QPLIB / Pooling / Stress / NLP**: Assorted LP and MIP sets in `data/*/reference.json`.
- **Case Studies**: Refinery LP/MIP instances dynamically generated by `bench/case_studies/refinery/generator.py`.

*Why train/test are disjoint*: The goal is to prove the branching rule generalizes across heterogeneous models. Testing on instances it trained on would compromise this claim.

*Pilot Instance Acquisition (2026-10-03)*: A disjoint pilot set was constructed from the official ZIB list (`https://miplib.zib.de/downloads/benchmark-v2.test`). The repository's reported instances (Tier 1, Tier 2, MIPLIB3, Case Studies) were explicitly subtracted by exact string matching against the benchmark names. A selection of observation-producing instances from the remaining disjoint pool was assigned to `train_instances.txt` and `test_instances.txt` for toolchain validation.

*Note*: This constitutes a small pilot collection set for toolchain validation only. It is not the final Issue #801 training/test split, which must be scaled and validated later.

## 2. Phase 1 CSV Data Collection
We will use the existing benchmark runner to collect data. The `mip_strong_branch_record_csv` option can be passed via:
`python bench/runners/miplib.py --solver-option mip_strong_branch_record_csv=bench/results/training_data.csv --instances <DISJOINT_LIST>`

Because the solver uses `std::ios_base::app` (append mode) and the Python runner solves instances sequentially, multiple instances will safely append candidate rows to the single CSV without interleaving.

## 3. Seed Policy
Issue #801 requires multi-seed evaluation. The repository's `bench/runners/miplib.py` already natively supports `python bench/runners/miplib.py --seeds 3`. This logically permutes rows and columns deterministically to evaluate numerical stability. The training set should ideally collect data across multiple seeds.

## 4. CSV Schema and Feature Constraints
The solver emits 12 columns per candidate:
1. `u` (variable index)
2. `fractionality` (Feature)
3. `objective_coefficient` (Feature)
4. `column_degree` (Feature)
5. `pc_down` (Feature)
6. `pc_up` (Feature)
7. `measured_down`
8. `measured_up`
9. `down` (effective)
10. `up` (effective)
11. `score` (effective)
12. `selected` (1/0)

**Excluded fields**: The model must only use features 2 through 6. It must explicitly exclude the true gains (`measured_down`, `measured_up`), the effective solver quantities (`down`, `up`, `score`), the candidate identifier (`u`), and the outcome (`selected`). 

## 5. Target Formula
The target is continuous regression mimicking the true strong-branching product score:
`target = max(measured_down, 1e-6) * max(measured_up, 1e-6)`

## 6. Data-Quality and Selection-Bias Checks
- **Unmeasured Rows**: A value of `-1` for `measured_down` or `measured_up` indicates the candidate was bypassed (e.g. not in the top N fractional candidates). The trainer strictly discards these rows to prevent predicting pseudocost heuristics.
- **Critical Selection Bias**:
  - The instrumentation captures ALL integer candidates considered for branching.
  - Only actually strong-branched candidates have measured targets (unmeasured are -1).
  - The Phase 2B trainer currently trains only on those measured rows.
  - Therefore, the resulting dataset is not yet representative of every candidate.
  - This must be considered during Phase 2D data collection/design.

## 7. Model Generation Constraints
- No reported instance must ever enter the training set.
- No learned rule will be generated or integrated into `src/mip/` until real training data is collected using this protocol.
